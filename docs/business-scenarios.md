# 业务场景与恢复规则

## 应传未传

一个应传窗口对应一个 Incident。相同设备、相同应传时刻的重复事件由业务键幂等；不同应传窗口独立建案，避免把不同原因混在一起。

首次调查会查询：应传时间、历史与当前网关状态、窗口内传输、计划变更以及匹配设备 Profile 的 SOP。

恢复判定由 Java 完成：

- 应传时网关离线或未绑定：后来任意一次网关传输可以证明链路恢复；
- 应传时网关在线：必须观察到后续真正的定时网关传输；
- 磁铁、事件、告警或小程序上传不能证明定时自动唤醒恢复；
- 在原应传时刻之前生效的改期可以使旧窗口失效。

未恢复时按设备传输周期安排综合复查，最多三次。每次创建新的 AgentRun 和 Graph thread，重新收集全部证据，不恢复已经完成的 Checkpoint。第三次仍未恢复则停止自动复查并转人工。

## 低电量

低电量 Agent 查询事件上下文、告警后的近期传输和当前网关状态。模型可以解释“可能相关”或“存在竞争原因”，但不能把相关性写成因果。Java Validator 输出影响评估，证据不足时进入人工复核。

## 传输事件不全

上游只有在实收事件数大于 0 且小于总数时才发布该异常。当前版本不运行 Agent，直接创建可审计的客服案件，由人工确认后走双人关单。
